# Counter_Core v1.0 接口规范

对标 Keysight 53230A 的 **gap-free 连续时间戳** 测量模型。

与 `Counter` v1.0 的根本区别：测量时序由硬件产生，时间戳经 AXI-Stream/DMA 连续流出，
软件不再用 `usleep` 摆闸门、也不再逐条轮询 FIFO。

---

## 1. 测量模型

```
                  ┌─────────────────────────────────────────┐
   clk_fx ──/1 /4►│ ts_engine   边沿捕获 + 粗计数 + TDC 细值 │
                  │             ↓                            │
   clk_fs ───────►│           异步 FIFO (可配深度)           │
                  │             ↓                            │
                  └─────────────┬───────────────────────────┘
                                │ 64-bit AXI-Stream (连续)
                                ▼
                   axis_data_fifo → axi_dma S2MM → HP0 → DDR
```

软件只做三件事：准备 DMA 缓冲 → 写 `CTRL.TS_EN` 启动 → 从 DDR 取走时间戳做回归。
采集期间 CPU 不参与搬运。

被测频率超过基准时钟奈奎斯特（>140 MHz）时无法逐边沿打时间戳，此时由 `PRESCALE.DIV4`
打开硬件四分频（见 3.4），时间戳法继续可用，软件把结果乘 4 还原。

另有一路外部 10 MHz 基准输入 `clk_10m`（V5），由 `SRC_SEL.SRC_10M`（见 3.5）顶替 `clk_fx`
送进同一个引擎。它按定义就是精确的 10 MHz，于是拟合结果反过来成了对 `clk_fs` 的测量，
用来反推基准时钟的实际频率 —— 见第 8 节。

等精度计数（`eq_counter`）已整体删除，测频只剩时间戳这一条路径。它的不确定度就是 ±1 计数
`1/(f_x·T_gate)`，350 MHz / 100 ms 闸门为 0.029 ppm，与实测完全吻合 —— 说明本该改善它的
闸门 TDC 校正从未真正生效（见 7.2）。同一闸门下时间戳法可达 0.00004 ppm。
对应的 `EQ_*` / `TDC_GATE` / `GATE_LEN` 寄存器与 `CTRL.EQ_START`、`STATUS.EQ_*` 一并移除。

## 2. 时间戳格式（64 位，小端写入 DDR）

| 位域 | 宽度 | 名称 | 说明 |
|------|------|------|------|
| [63:32] | 32 | `coarse` | `clk_fs` 域自由计数，1 LSB = 1/f_s（3.2 ns @312.5 MHz），13.7 s 绕回 |
| [31:24] | 8 | `tdc` | TDC 细值 0~255，亚周期插值 |
| [23] | 1 | `ovf` | 溢出标记：**本条之前**发生过丢失。⚠ **实测未按设计置位，当前不可信**，见 7.4；判断间隙请用 `coarse` 增量 |
| [22] | 1 | `tdc_ok` | TDC 细值有效。为 0 表示该 `clk_fs` 周期内延迟链未捕获到跳变，细值不可信，回归时应剔除该点 |
| [21:0] | 22 | `seq` | 条目序号，每条 +1，419 万条绕回 |

> 延迟链从 64 抽头加长到 256 后，`tdc` 从 6 位扩到 8 位，占用的两位取自 `seq`。
> `seq` 只需在单次采集内不绕回，22 位对应 419 万条 / 33 MB 缓冲，远超实际用量（4096 条）。

软件还原时刻：

```c
double t = ((double)coarse + (double)tdc / 256.0) / f_s;
```

`seq` 用于校验连续性 —— gap-free 的语义是"要么一条不丢，要么明确告诉你哪里丢了"。
`ovf` 置位或 `seq` 跳变即表示该点之前存在间隙，回归时应在此处断开分段。

> 一条 64 位固定对齐 8 字节，HP0 为 64 位口，无需 upsizer。
> 因此 `C_M_AXIS_TDATA_WIDTH` 从模板的 32 改为 **64**，BD 中 `axis_data_fifo_0`
> 与 `axi_dma_0` 的 stream 宽度需同步改为 64。

## 3. 寄存器映射

基地址偏移，全部 32 位。地址空间 256 字节（`C_S_AXI_ADDR_WIDTH = 8`）。

| 偏移 | 名称 | 访问 | 说明 |
|------|------|------|------|
| 0x00 | `CTRL` | R/W | 控制位，见 3.1 |
| 0x04 | `STATUS` | R | 状态位，见 3.2 |
| 0x08 | `EDGE_SKIP` | R/W | 每 `N+1` 个边沿采一条。0 = 每个边沿都采。**测频时应调大以拉长时间跨度换精度**，见 5.1 |
| 0x0C | `TS_COUNT` | R | 已成功写入 FIFO 的时间戳总数 |
| 0x10 | `LOST_COUNT` | R | 因 FIFO 满而丢弃的边沿数。gap-free 成立时应恒为 0 |
| 0x14 | — | — | 保留。原 `GATE_LEN` / `EQ_STAND` / `EQ_TEST` / `TDC_GATE`，等精度路径已移除，读作 0 |
| 0x24 | `FIFO_LEVEL` | R | 当前 FIFO 中未取走的条目数（调试用） |
| 0x28 | `VERSION` | R | 魔数 `0x43430102` = "CC" + v1.02（加 `PRESCALE` 时从 `0x43430100` 递增，加 `SRC_SEL` 时再增一次） |
| 0x2C | `TS_PKT_LEN` | R/W | M_AXIS 包长（拍）。每 N 拍产生一个 TLAST。0 = 不产生 TLAST，**simple mode 下会导致 DMA 永不结束**，见下方说明 |
| 0x30 | `PRESCALE` | R/W | 被测信号预分频，见 3.4 |
| 0x34 | `SRC_SEL` | R/W | 测量源选择，见 3.5 |

> **`TS_PKT_LEN` 必须设成 DMA buffer 的条数，不能填 0。**
>
> axi_dma 的 S2MM 通道靠 `TLAST` 界定一次传输的结束，"收满 buffer length"
> 本身不构成结束条件。填 0 时通道会一直停在 busy 状态，`XAxiDma_Busy()`
> 永不返回 false，表现为超时 —— 尽管数据其实已经写进 DDR 了。
>
> 实测现象：2 秒超时窗口内 `TS_COUNT + LOST_COUNT` 与被测频率完全吻合
> （边沿一个没丢），但 `XAxiDma_Busy()` 始终为真。填 `TS_PKT_LEN = entries`
> 后 TLAST 正好落在缓冲区最后一个字上，传输正常结束。
>
> 0 这个取值保留给 SG 模式的连续环形传输场景，simple mode 不适用。

未列出地址读作 0，写忽略。

### 3.1 CTRL (0x00)

| 位 | 名称 | 说明 |
|----|------|------|
| 0 | `TS_EN` | 1 = 时间戳引擎持续采集并向 M_AXIS 输出 |
| 1 | `TS_RST` | 1 = 复位引擎（清 FIFO、计数、序号、溢出标志）。电平有效，需自行拉低 |
| 2 | — | 保留（原 `EQ_START`，等精度已移除） |
| 3 | `SOFT_RST` | 1 = 复位整个测量核心 |
| 31:4 | — | 保留 |

### 3.2 STATUS (0x04)

| 位 | 名称 | 说明 |
|----|------|------|
| 0 | `TS_RUNNING` | 时间戳引擎正在采集 |
| 1 | `OVERFLOW` | **粘滞**溢出标志，发生过丢失即置位，由 `TS_RST` 清除 |
| 4 | `FIFO_EMPTY` | 时间戳 FIFO 为空 |
| 31:5 | — | 保留 |

### 3.4 PRESCALE (0x30)

| 位 | 名称 | 说明 |
|----|------|------|
| 0 | `DIV4_EN` | 1 = 被测信号四分频后再送时间戳引擎。软件必须把测得频率乘 4 |
| 31:1 | — | 保留 |

只影响 `ts_engine`。

**为什么需要它。** `ts_engine` 把 `clk_fx` 当**数据**在 `clk_fs` 域采样，要求高、低电平各自
都长于一个 `clk_fs` 周期（3.2 ns）。四分频输出取自计数器 bit1，恒为 50% 方波，且分频后
上升沿**就是**输入的上升沿（只多一级触发器的固定延迟），所以没有任何时序信息损失 ——
固定延迟在最小二乘斜率里完全抵消。

**为什么单独占一个寄存器而不用 `CTRL` 空闲位。** 现有软件对 `CTRL` 全是绝对写
（`core_wr(CTRL, CTRL_TS_EN)`），不是读改写；分频位放进 `CTRL` 会被采集流程自己清掉，
现象是高频读数恰好偏低 4 倍，而所有连续性与自检判据照样通过。

**约束：只能在 `CTRL.TS_EN` 为低时改写。** RTL 里选择端是组合逻辑，不像 `EDGE_SKIP`
那样在采集起始沿锁存；采集中途改写会破坏正在进行的这一次。

**量程**（`f_s` = 312.5 MHz，按紧到松）：

| 约束 | 上限 | 说明 |
|------|------|------|
| XDC `clk_fx` 约束 2.857 ns | **350 MHz** | 当前实际上限。要更高须收紧约束 |
| TDC 链跨度 5.376 ns（256 × 21 ps） | ~372 MHz | 分频后半周期须长于链跨度，否则链里同时残留上一个下降沿，温度计码被污染 |
| `clk_fs` 电平采样 | 562.5 MHz | 分频后 ≤ 140.625 MHz |
| BUFG 最高频率（-1 器件） | ~460 MHz | 物理天花板 |

四分频恰好是够用的最小 2 的幂：二分频后 175 MHz 超奈奎斯特；四分频后 87.5 MHz，
半周期 5.71 ns 刚好越过 5.38 ns 链跨度（余量 6%）。

> 链跨度这条约束在分频之前就存在。7.1.1 记的"99 MHz 的 σ 比 5 MHz 差 1.7 倍、
> `tdc` 取值范围只有 4~31"很可能就是它 —— 99 MHz 半周期 5.05 ns 已经短于链跨度。
> 分频反而让高频段的 TDC 质量优于现在的 99 MHz。

### 3.5 SRC_SEL (0x34)

| 位 | 名称 | 说明 |
|----|------|------|
| 0 | `SRC_10M` | 1 = 时间戳引擎测量外部 10 MHz 基准 `clk_10m`（V5），而不是 `clk_fx` |
| 31:1 | — | 保留 |

置位时硬件**旁路预分频**，`PRESCALE` 被忽略 —— 10 MHz 远在奈奎斯特之下，没有需要分频的东西，
而且让 `clk_10m` 去驱动分频计数器就等于让它当时钟，这恰是这个输入被设计成"只作数据"要避开的。
两个选择端在 RTL 里合成同一个 LUT3，接在延迟链之前，所以切到 10 MHz 源不增加关键路径深度。

与 `PRESCALE` 同样的两条规矩：

- **只能在 `CTRL.TS_EN` 为低时改写**，选择端是组合逻辑，不在采集起始沿锁存。
- **单独占一个寄存器**，不放 `CTRL` 空闲位 —— 软件对 `CTRL` 全是绝对写，放进去会被采集流程自己清掉。

残留一个 `SRC_10M` 比残留一个 `DIV4_EN` 更难发现：之后每一次测频都报 10 MHz，
而连续性检查、间隔统计、拟合残差全部正常。因此每个启动采集的软件函数都显式声明自己要哪个源。

用途见第 8 节。

## 4. 软件使用流程

### 4.1 时间戳模式（唯一测频路径）

```c
// 0. 预分频：f_x > 0.9 × f_s/2 时开四分频，读数最后乘 4
WriteReg(PRESCALE, (f_x > safe_limit) ? PRESCALE_DIV4 : 0);

// 1. 准备 DMA 接收缓冲（cache 一致性见下方注意）
XAxiDma_SimpleTransfer(&dma, (UINTPTR)buf, len, XAXIDMA_DEVICE_TO_DMA);

// 2. 复位并配置引擎
WriteReg(CTRL, CTRL_TS_RST);
WriteReg(EDGE_SKIP, skip);
WriteReg(CTRL, 0);

// 3. 启动采集 —— 硬件持续产流，CPU 空闲
WriteReg(CTRL, CTRL_TS_EN);

// 4. 等 DMA 完成中断（或轮询），期间可做别的事

// 5. 停采
WriteReg(CTRL, 0);

// 6. 取数前必须失效 cache，HP0 不经 ACP
Xil_DCacheInvalidateRange((UINTPTR)buf, len);

// 7. 校验连续性后做最小二乘回归
if (ReadReg(STATUS) & STATUS_OVERFLOW) { /* 存在间隙，分段处理 */ }
```

### 4.3 等待 DMA 完成：不要用 `XAxiDma_Busy()`

```c
/* 错误：Busy() 查 IDLE 位，缓冲填满瞬间软件停不掉引擎，
   多余数据砸向已完成的通道 -> DMAIntErr -> halted，
   而 halted 的通道永远不置 IDLE，于是死等到超时 */
while (XAxiDma_Busy(&dma, XAXIDMA_DEVICE_TO_DMA)) { ... }

/* 正确：IOC 在完成时锁存，且能挺过随后的错误 */
while (!(XAxiDma_ReadReg(base, XAXIDMA_RX_OFFSET + XAXIDMA_SR_OFFSET)
         & XAXIDMA_IRQ_IOC_MASK)) { ... }
WriteReg(CTRL, 0);                       /* 立刻停采 */
/* 清中断锁存位；若 halted 则 reset 通道，为下次采集备好 */
```

尾部的 `DMAIntErr` 是"缓冲已满但引擎还在推"的必然副作用，
不影响已落盘的数据。传输前也要清一次状态位，否则上次遗留的 IOC
会让本次瞬间"完成"。

## 5. 性能边界

gap-free 不是无条件成立的，上限由三处决定：

| 限制 | 数值 | 后果 |
|------|------|------|
| `clk_fs` 域每周期最多产 1 条 | 312.5 M 条/s | 硬上限 |
| HP0 带宽（64bit @150MHz，留余量） | ~800 MB/s ÷ 8 B = 1e8 条/s | 超出则 FIFO 积压 |
| 送进引擎的信号需在 `clk_fs` 域可采样 | < f_s/2 = 156 MHz | 超出须开 `PRESCALE.DIV4`，见 3.4 |

**实用结论**：f_x ≤ 100 MHz 且 `EDGE_SKIP = 0` 时可真 gap-free。

`LOST_COUNT` 与 `STATUS.OVERFLOW` 是判据：只要它们为 0，本次采集就是真正无间隙的。

### 5.1 `EDGE_SKIP` 是提精度的手段，不是降速的妥协

容易误解成"抽稀 = 牺牲数据"。实际相反：**测频精度由时间跨度决定，不由样本数决定。**

最小二乘斜率的不确定度：

```
sigma_slope = sigma_t * sqrt(12) / N^1.5
```

相对精度 = `sigma_slope / slope`，而 `slope` 正比于相邻取样点的间隔，
也就是正比于整段序列覆盖的时间跨度。缓冲区容量固定为 N = 4096 时：

| 配置 | 时间跨度 | 相对精度（理论） |
|------|----------|------------------|
| `EDGE_SKIP = 0` | 0.82 ms | ~0.009 ppm |
| `EDGE_SKIP = 134` | 110 ms | **~0.00007 ppm** |

`sigma_t`（TDC 的 133 ps）与 N 都没变，仅仅因为分母的 `slope` 大了 135 倍，
精度就好 135 倍。跳过的边沿并不浪费 —— 回归真正依赖的是首尾之间的时间基线，
中间样本只贡献 `sqrt(N)` 量级的改善。

> 理论值 0.009 ppm 与 `EDGE_SKIP=0` 下的实测极差 0.005 ppm 吻合（见第 7.1 节），
> 说明该模型可信，外推到长跨度有意义。110 ms 那一档尚未实测，
> 实际会先撞上 OCXO 短期稳定度与温漂，而非本公式的极限。

### 5.2 两种用途的取舍恰好相反

| 目的 | 配置 | 理由 |
|------|------|------|
| **测单个频率值** | 用 `EDGE_SKIP` 把跨度拉满闸门 | 跨度决定精度，见上 |
| **相位噪声 / Allan 方差 / 抖动分析** | 必须 `EDGE_SKIP = 0` | 需要每一个边沿的连续序列，跳过就丢失了抖动的时间结构 |

第二类才是 gap-free 不可替代的地方：它的价值不在于让单次测频更准，
而在于**一个边沿都不丢**。等精度法在这类分析上完全无能为力。

`ReadFr_TimestampMode()` 走的是第一类：按 `GATE_TIME` 反算 `EDGE_SKIP`，
让 4096 条样本铺满整个闸门时间。诊断用的 `TimestampTest()` 则直接指定条数与
`EDGE_SKIP`，不参考 `GATE_TIME`。

| # | 问题 | 位置 | 处理 |
|---|------|------|------|
| 1 | 边沿检测方向与命名相反（实为下降沿） | `timestamp_engine.v:79` | 统一为上升沿，与 TDC 测量边沿一致 |

| 6 | 闸门参数寄存器未接硬件，闸门靠 `usleep` | `Counter_v1_0_S_AXI.v` | `GATE_LEN` 接硬件定时器 |
| 7 | 闸门经两个时钟域各自同步，开启时刻差最多 3 拍 | `cymometer.v` | 闸门单域产生后分发，差值固定可校正 |
| 8 | TDC 编码器遇气泡码取错位置 | `tdc.v` popcount 级 | 改为统计 1 的个数，气泡免疫 |
| 9 | FIFO 状态拼接 33 位赋给 32 位被截断 | `Counter_v1_0_S_AXI.v:1403` | 状态位重新分配到 `STATUS`/`FIFO_LEVEL` |
| 10 | M_AXIS 发模板假数据 | `Counter_v1_0_M_AXIS.v` | 接真实时间戳流 |

## 7. 实测数据

2026-08-14，xc7z020，基准 312.5 MHz，被测 5 MHz 与 99 MHz。

### 7.1 gap-free 已达成

连续两次采集，结果完全一致：

```
第一次                          第二次
TS_COUNT   4516                 TS_COUNT   4516
FIFO_LEVEL 420                  FIFO_LEVEL 420
delta mean 62.500               delta mean 62.500
tdc_ok     4096/4096            tdc_ok     4096/4096
LOST_COUNT 0, ovf marks 0       LOST_COUNT 0, ovf marks 0
sequence contiguous, seq 起于 0  sequence contiguous, seq 起于 0
f (fit)    4999999.988 Hz       f (fit)    4999999.991 Hz
```

| 指标 | 实测 |
|------|------|
| 连续时间戳 | 4096 条无间隙 |
| 采集耗时 | ≈ 819 μs |
| 频率误差 | **0.002 ppm** |

对照等精度模式：100 ms 闸门得到 0.029 ppm。
**时间戳法用 1/122 的时间，拿到好 14 倍的精度** —— 这是换成 53230A 模型的全部意义。

三个数字互相印证：

- `TS_COUNT − 4096 = 420 = FIFO_LEVEL`，即采够 4096 条后 `pop_cnt` 触顶停止
  弹出，其后产生的 420 条留在 FIFO 内、没有外溢到下游
- 420 条 = 84 μs，正落在 100 μs 轮询间隔内
- 两次 `coarse` 起点不同（54294 / 58042），确认是两批新数据而非同一份

`delta` 在 62 与 63 之间严格交替、均值恰为 62.5（= 312.5/5），是粗计数与
边沿检测流水线对齐正确的硬证据；若对齐错一拍，这个均值会明显偏离。

### 7.1.1 长跨度测频（`ReadFr_TimestampMode`，闸门 100 ms）

各 10 次连续测量，`EDGE_SKIP` 由 `GATE_TIME` 反算，4096 条样本铺满整个闸门：

| 被测 | `EDGE_SKIP` | 跨度 | 标准差 σ | 极差 | 平均偏离标称 |
|------|-------------|------|----------|------|--------------|
| 5 MHz | 134 | 110 ms | **0.000022 ppm** | 0.000074 ppm | +0.0000048 ppm |
| 99 MHz | 2684 | 111 ms | **0.0000375 ppm** | 0.000119 ppm | −0.0000078 ppm |

两者跨度相近而 σ 相差约 1.7 倍，可能来自 TDC 在两个频率下的相位分布不同
（`tdc` 取值范围 20~40 对 4~31），也可能是信号源本身，未进一步区分。

`delta` 均值分别为 62.500（= 312.5/5）与 3.157（= 312.5/99），均与理论吻合。

> **注意**：312.5/5 与 312.5/99 都接近简单比值，若信号源与基准共用同一
> 10 MHz 参考，则测得的是精确比值，**平均值贴近标称说明不了绝对准确度**。
> 上表中 σ 与极差反映的是系统分辨率，这部分不受同源影响；平均值一列
> 仅供参考。要验证绝对准确度需换用独立参考的信号源。

### 7.1.2 带宽上限：99 MHz 无法 `EDGE_SKIP = 0`

99 MHz 每边沿 8 字节 = **792 MB/s**，已贴着 HP0 实际带宽。实测
`TimestampTest(4096, 0)` 在 99 MHz 下首次采集必然丢数据：

```
coarse 49159 -> 54187, gap delta=5028, next delta=3     (≈16 us ≈ 1580 个边沿)
LOST_COUNT 1798
```

FIFO 4096 条在 99 MHz 下只够撑 41 μs，而 DMA 首次配置就要十几微秒，
这段时间内 FIFO 必然填满并开始丢弃。第二次采集通常正常（DMA 已就绪）。

**这是带宽物理限制，不是缺陷。** 连续流采集的实用上限约 50 MHz；
更高频率必须使用 `EDGE_SKIP`，而测频场景本来就该那么用（见 5.1）。

### 7.2 TDC 延迟链：三处接线错误（已修）+ 量程不足（已加长到 256 抽头）

原始现象：`tdc_test_rise` 90% 以上饱和在 63，等精度的 TDC 校正退化成
+0.83 周期的固定偏置，100 ms 闸门上表现为恒定 +9.4 Hz 误差；
`tdc_fall` 有 80% 落在 4 的倍数上（均匀分布只该有 25%）。
当时归因为"实际分辨率约 133 ps/tap，链总跨度约 1.9 ns"。

**这个归因只对了一半。** 逐条审查 `tdc.v` 后发现三处结构性错误：

| # | 错误 | 后果 |
|---|------|------|
| 1 | 级联取 `CO[0]` 而非 `CO[3]` | `CO[0..2]` 是普通组合输出走通用布线，只有 `CO[3]` 接专用 `COUT`。每级只推进 1 个进位延迟却读走 4 个抽头，块内四抽头几乎同时翻转 —— 这就是"80% 是 4 的倍数"和"133 ps/tap"的真正来源 |
| 2 | `O` 输出反相未补偿 | `S=1111` 时 `O[j] = S[j] XOR CI_j = ~CI_j`，读数是 `NUM_TAPS − 距离` 而非距离本身，与文件头注释所述相反 |
| 3 | 首级信号从 `CI` 注入 | `CI` 在硅上只接上一级 `COUT`，通用信号必须走 `CYINIT` |

修复后（`CO[3]` 级联、popcount 级取反补偿、首级改用 `CYINIT`）实测：

```
mult-of-4  217 permille   （250 = 均匀期望，修复前 800）
t_tap      21.0 ps        （修复前表观 133 ps）
链跨度     1.35 ns        （64 抽头）
```

分辨率提升约 6 倍，**但总跨度基本没变** —— 物理链长由 16 个 CARRY4 决定，
错误级联损害的是分辨率而非长度。所以原归因里"链盖不满一个周期"这条依然成立，
且成为修复后唯一剩下的瓶颈：64 抽头只覆盖 3.2 ns 周期的 42%，58% 的样本饱和。

**布局无需人工约束。** 改用 `CO[3]` 后级联走 `COUT → 正上方 slice 的 CIN` 硬连线，
布局器别无选择。routed 检查点实测时间戳链为单列连续（`SLICE_X62Y62..Y77`，
当时另有一条等精度链 `SLICE_X58Y75..Y90`，现已随等精度路径删除），
`tap_reg` 的 64 个触发器落在同一 Y 范围内，采样偏斜已最小化。
`scripts/tdc_chain_report.tcl` 可复查。

**加长到 256 抽头。** 128 被否决：慢角 25 ps/tap 恰好只够覆盖周期、零余量，
典型角就不够了。256 抽头在典型角跨约 5.4 ns，且正好吃满 8 位 `tdc_value`。
`NUM_TAPS` 必须保持 2 的幂 —— `tdc.v` 的饱和判定靠"只有满计数才置最高位"，
这个技巧只在 2 的幂下成立。

连带改动：流水线从 3 级增至 5 级（`TDC_LATENCY = 5`），
`ts_engine` 的抽头随之改为 `edge_d4` / `free_run_cnt_d5`，推导见 `tdc.v` 头部的 timing contract。

⚠ **256 抽头版本尚未上板验证。** 待 `TdcHistogramTest` 确认饱和消失
（past-end 接近 0、256 个码全覆盖）并完成码密度标定。

### 7.3 硬性约束：引擎只能在 DMA 已 armed 的前提下开启

**违反这条会污染一块软件清不掉的缓冲区，且现象极难识别。**

调试期曾在 `init_freqcounter()` 里放一段"活性测试"：不启动 DMA，
只把 `CTRL.TS_EN` 拉高跑 1 ms，靠 `TS_COUNT` 确认引擎在动。它确实证明了
引擎正常，代价是把约 5000 条时间戳推进了 `axis_data_fifo`。

`CTRL.TS_RST` 只能复位 `ts_engine` 内部的 FIFO，**够不到下游的
AXI-Stream FIFO 和 DMA 内部缓冲**。于是后续每次采集都先从下游搬走陈货：

```
1 ms 活性测试   → 4998 条灌入下游（实测该缓冲可存约 4700 条）
第一次采集      → DMA 收满的 4096 条全是陈货，新数据只产生 505 条
第二次采集      → 继续搬剩下的 601 条，之后才是新数据 → seq 在 601 处断裂
```

**为什么难以识别**：`TS_RST` 会把 `seq` 归零、把 `free_run_cnt` 归零，
所以陈货与新数据在数据层面完全同构 —— `seq` 连续、`delta` 严格 62/63、
`tdc_ok` 满分、连毒值填充都被完整覆盖（DMA 确实写满了每个格子，
只是写的是旧内容）。**所有判据全部通过。**

唯一露出破绽的是 `TS_COUNT`（报 504 而非约 4500）—— 而它恰恰被先后错怪了
三次：先归咎于 TLAST 缺失、再归咎于 `cnt_cdc` 时序违例、又归咎于接线错误。
它自始至终是对的。

**硬件侧的防护**（已实现）：`ts_engine` 的弹出受 `stream_en` 与 `pkt_limit`
双重门控 —— `TS_EN` 为低时不弹出，弹够 `pkt_limit` 条也停，直到 `TS_EN`
落下才重新武装。这保证一次采集只有一个包离开，其后产生的数据留在内部
FIFO 等待 `TS_RST` 清除（实测 `TS_COUNT − 4096 = FIFO_LEVEL = 420`）。

但这只防未来，**清不掉已经躺在下游的存货**。所以规矩仍然成立：
开引擎前必须先 arm DMA。

> **附带说明 `cnt_cdc`**：追查此问题期间，`cdc.v` 的格雷码转二进制
> 从串行涟漪改成了并行 XOR 归约。当时的理由（32 位 31 级链在 100 MHz
> 下不收敛）**是错的** —— 串行版本一直读得正确。改动本身仍然保留，
> 因为把 31 级组合链交给布局器毫无必要，但它属于预防性改进，
> 不是对已观察故障的修复。
>
> 同理，`LOST_COUNT == 0` 这个判据没有问题。但真正独立可信的判据
> 依然是 `TS_COUNT` 与 `FIFO_LEVEL` 的自洽关系，以及毒值填充 ——
> 单看数据本身的连续性是不够的。

#### 7.3.1 同一机制的小剂量版本：每次采集残留一条

即使不违反上述规矩，正常采集也会给下一次留下**一条**陈货：DMA 收满
缓冲区停止接收时，`axis_data_fifo` 里可能还压着一条已弹出但未被取走的
记录，而 `TS_RST` 同样够不到它。

识别方法确凿 —— `TS_RST` 会把 `free_run_cnt` 归零，所以陈货的 `coarse`
必然**远大于**紧随其后的新数据，表现为时间倒流：

```
[TS] dropped stale leading entry (coarse 33609969 > 54308)
                                  ^107 ms，上次采集的长度   ^174 us，本次
```

`CaptureTimestamps()` 内置了软件规避：检测到 `coarse[0] > coarse[1]` 就丢弃
首条并前移，代价是有效条数少一条（4096 → 4095），对回归精度无影响。
实测 10 次测量中约 4 次触发。

**硬件根治（`stream_aresetn` 输出）**

IP 顶层新增输出 `stream_aresetn`（`aclk` 域，低有效），驱动源是内部的
时间戳引擎复位 `ts_rst_ax_n`。在 BD 中把它接到 `axis_data_fifo_0` 的
`s_axis_aresetn`，取代原本的全局复位，`CTRL.TS_RST` 就会同时清空
IP 内部 FIFO 与下游 FIFO，残留从源头消失。

打包脚本已将该端口标注为 `xilinx.com:signal:reset:1.0` 接口并声明
`POLARITY = ACTIVE_LOW`；不声明极性的话 Vivado 会按高有效处理，
自动连线时插入反相器，结果正好相反。

> 软件规避保留不动：它是双保险，且在 BD 尚未改线时仍然有效。
> 两者同时生效也不冲突 —— 没有残留时规避条件不成立，不会误删数据。

### 7.4 待查：`ovf_mark` 未按设计置位

`ts_engine` 的设计意图是：发生丢弃后，恢复写入的第一条时间戳应带
`ovf_mark = 1`（bit[23]），供软件定位间隙。

实测不成立。99 MHz 下确实丢了约 1580 条边沿、`LOST_COUNT = 1798`，
但缺口后那条记录的 `ovf = 0`，整个缓冲区 `ovf marks 0`：

```
coarse 49159 -> 54187, gap delta=5028, next delta=3
seq 0 -> 1, ovf=0        <- 应为 1
```

按 RTL 逻辑，`wr_drop` 会置 `ovf_mark`，随后的 `wr_en` 在打包 `ts_word`
时应读到该值。实际行为与之不符，定位需要仿真或 ILA。

**当前影响可控**：缺口由 `VerifyContinuity()` 的 `coarse` 增量检查捕获，
不依赖此标志。但 `ovf_mark` 这个字段目前**不可信**，软件不应据它判断。

## 8. 外部 10 MHz 基准校准

### 8.1 原理

时间戳引擎测的始终是一个**比值**：被选中的输入的一个周期里装得下多少个 `clk_fs` 周期。
平时 `clk_fs` 是已知的那一侧，输入是待测的那一侧。把一个**按定义就精确等于 10 MHz** 的源
接进来，两侧的角色就调转了 —— 拟合出来的"频率"其实是对 `clk_fs` 的一次测量。

设 `f_meas` 是软件按标称 `f_s,nom = 312 500 000 Hz` 算出的读数，则

```
f_meas / 10 MHz = f_s,nom / f_s,actual

f_s,actual = f_s,nom × 10 MHz / f_meas
```

读数偏高说明 `clk_fs` 实际偏慢，反之亦然。全程用标称值而不是 `GetClkFsFreq()`：
结果不能依赖当前已经装载了哪个校准值，也不能依赖 `CTR_STATUS0` 的位置，
两个标称因子在比值里本来就互相抵消。

### 8.2 硬件

`clk_10m` 是单端 LVCMOS33 输入，管脚 **V5**，走 `IBUF` 进来后直接送 `counter_core` 的源选择
多路器，**不上 BUFG**。它不驱动任何寄存器的时钟端：`ts_engine` 把它和 `clk_fx` 一样当数据，
在 `clk_fs` 域采样，TDC 延迟链也只是把它当输入信号。上全局缓冲既要占一个 BUFG，
又要为一个非时钟专用管脚申请 `CLOCK_DEDICATED_ROUTE` 豁免，却不改变任何逻辑行为。

XDC 里仍然对它 `create_clock -period 100.000` 并放进异步时钟组 —— 声明成时钟不是为了驱动谁，
而是让它到 `clk_fs` 域的跨域路径落进 `set_clock_groups -asynchronous` 的覆盖范围。
不声明的话这条路径整个落在时序分析之外，正是这份 XDC 当初为 `clk_fs` / `clk_fx` 补上的那个洞。

**外部 10 MHz 同时通到 PLL，校准前必须切断这条路。** 板上这一路 10 MHz 除了进 FPGA，还接到
LMK5B12204 的 `PRIREF_P` / `PRIREF_N`。`CTR_PRIREF`（W15）为高时 PLL 就把 312.5 MHz 锁到这个
外部 10 MHz 上 —— 此时再去测，读数必然是精确的 312.5 MHz，与 OCXO 的真实状态无关。
**校准要找的那个量恰好被锁没了，而所有判据仍然全部通过。** 因此校准前必须
`CTR_REF_CLOCK = 1`、`CTR_PRIREF = 0`，把 10 MHz 只留给计数器。
`init_freqcounter()` 上电把两者都置 1，所以刚开机的仪器一定要先做这一步（见 8.6）。

### 8.3 通约性：为什么这里不像 TDC 码密度那样要求失谐

`TdcHistogramTest` 要求输入与基准**不可通约**，否则相位不扫、直方图退化成几根尖峰。
10 MHz 对 312.5 MHz 恰好是 1:31.25，是可通约的，但对校准无害：

- 若 OCXO 偏差为零，相位完全不动，`tdc` 恒取那几个值。它们的查表误差是一个**常数偏移**，
  在最小二乘斜率里整体抵消，结果仍然正确。
- 若偏差为 δ ppm，100 ms 闸门内累积相移 = 100 ms × δ×10⁻⁶。δ = 1 ppm 时是 100 ns，
  合 31 个 `clk_fs` 周期 —— 相位扫过 31 圈，查表误差被平均掉。
- 中间状态（相位只扫过部分码）残留的误差量级是"TDC 查表误差 ÷ 总跨度"，
  几 ps ÷ 100 ms ≈ 10⁻¹¹，即 0.00001 ppm，比 OCXO 本身的短稳低两个数量级。

换句话说，偏差越小相位越不动、误差越接近纯常数；偏差越大相位扫得越充分、平均得越好。
两头都收敛，中间那段的残差也可以忽略。

### 8.4 软件流程

`CalibrateRefClk()`（`freq_counter_core.c`）：

1. **前置检查：`CTR_STATUS0` 与 `CTR_STATUS1` 必须都读到 1**，否则不做任何测量，
   直接返回 `CAL_ERR_PRECOND`
2. `PRESCALE = 0`、`SRC_SEL.SRC_10M = 1`
3. 把 `GATE_TIME` 临时改成固定的 **1000 ms**（`CAL_GATE_TIME_MS`），采一次时间戳并做
   最小二乘拟合（与普通测频共用 `measure_timestamp_freq()`，此时 `edge_skip` 自动定到
   2711，4096 条样本铺满整个闸门）
4. **无论成功失败都先还原 `GATE_TIME` 并把 `SRC_SEL` 清零**
5. 按 8.1 反推 `f_s,actual`
6. 合理性窗口：推算值必须落在 **312.49 ~ 312.51 MHz**（`CAL_FS_MIN_HZ` / `CAL_FS_MAX_HZ`）之内，否则拒绝，不写卡
7. 写入 `g_clk_fs_freq_sd`，再写 SD 卡 `FREQ.TXT`

第 1 步里 `CTR_STATUS0` 的理由是明确的：它决定校准值是否参与运算（见 8.5），为低时校准
等于花一秒钟算出一个仪器随后并不使用的数，还顺手覆盖掉卡上原有的值。`CTR_STATUS1`
在本工程里没有文档化的含义，代码把它当作校准前置条件是因为操作规程如此要求，
而不是因为固件知道它代表什么。

第 5 步不是形式主义。没接信号、接错频率、或者烧的是不带 `SRC_SEL` 的旧 bitstream
（写 0x34 落在不解码的地址上，实际测的是 `clk_fx`）—— 这三种情况都会得出一个
外观完全合理的数字并写进 SD 卡，此后每一次测频都按那个错误基准偏移。
312.49 ~ 312.51 MHz 相当于标称的 ±32 ppm，对 OCXO 而言仍然很宽（偏几十 ppm 的 OCXO 是坏了
而不是没校准），但足以拦住上面三种，也拦得住"V5 上接的其实是 10.002 MHz"这类接近但不对的源。
判据取在推算出的基准频率上而不是 ppm 偏差上，是为了让上下限就是操作者能从规格书上
直接读到的两个数。

旧 bitstream 这一路另有一道防线：`VERSION` 魔数从 `0x43430101` 升到 `0x43430102`，
`init_freqcounter()` 是等值比较，版本不符直接报错退出。

**为什么闸门写死而不跟随 `FREQ:GATE:TIME`。** 拟合精度取决于样本覆盖的时间跨度，
沿用配置值意味着操作员把闸门留在 100 ms 默认值时，校准精度直接差十倍。
而这个数字不是一次可以重测的读数 —— 它进 SD 卡，此后每一次测频都以它为基准。
一秒钟花得起。

### 8.5 生效条件

写进 `FREQ.TXT` 的值**并不立即参与运算**。`GetClkFsFreq()` 由 `CTR_STATUS0` 选择：

| CTR_STATUS0 | 使用的基准频率 |
|-------------|----------------|
| 1 | SD 卡中的校准值 |
| 0 | 理想值 312 500 000 Hz |

`CTR_STATUS0` 为低时 `CalibrateRefClk()` 直接拒绝执行（见 8.4 第 1 步），
所以「校准成功」与「校准值正在生效」在本实现里是同一件事。

### 8.6 上位机接口

两条 SCPI 命令，必须按顺序使用：

| 命令 | 作用 |
|------|------|
| `CAL:REF:PREP` | 置 `CTR_REF_CLOCK = 1`、`CTR_PRIREF = 0`，把外部 10 MHz 从 PLL 上摘下来（见 8.2）。响应 `1` |
| `CAL:REF?` | 执行校准。响应 `1`（已推算、落在 312.49 ~ 312.51 MHz 之内、已写入 SD 卡）或 `0`（其余一切情况）|
| `CAL:REF:VAL?` | 查询当前正在使用的基准频率，53230A 科学计数法，单位 Hz。读的是 `GetClkFsFreq()`，即受 `CTR_STATUS0` 选择的那个值 |

`CAL:REF?` 反推出的频率值和拒绝原因都打在串口 —— 它的响应回答的是"仪器现在校准好了没有"，
不是一个测量结果。一次调用固定耗时约 1.1 秒（1 s 闸门，4096 条样本略微溢出闸门），期间占用连接。

`CAL:REF:PREP` 只是两次寄存器写，立即返回；但 PLL 换参考源之后需要时间重新稳定，
固件不替上位机等待，两条命令之间应当留出间隔。

固件不检查 `CAL:REF:PREP` 是否执行过 —— 这两个引脚是纯输出，读回来的是软件刚写进去的值，
证明不了 PLL 已经切换完毕，做这种检查只会给出虚假的安全感。详见 `protocols/上位机通信协议.md`。
